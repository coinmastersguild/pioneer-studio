# Backend asks — Pioneer API

Three requests from Pioneer Studio, ordered by what they unblock. Verified
against `alpha.pioneers.dev` on 2026-07-25.

---

## 1. `POST /api/v1/motion/extract` — video → ARDY skeleton

**The gap.** The motion service generates motion from text and nothing else.
`/api/v1/motion/{extract,estimate,from_video,track}` and `/api/v1/pose/extract`
all 404. There is no pose estimator anywhere in the jobs list either (13 models:
flux ×3, acestep, wan-s2v, ltx-2.3 ×2, ltx-enhance, voxcpm2 ×2, sfx-audiogen).

**What we shipped meanwhile.** `src/poseExtract.ts` runs MediaPipe's pose
landmarker in the browser and redraws the result as a cskel27-topology control
take (768×448, 24fps, the shape `enhance` wants). It works and it costs nothing,
but it is strictly worse than a server implementation in two ways:

- It is **2D screen-space only**. The skeleton keeps the source video's framing,
  so you inherit that camera. A server-side extract returning cskel27 *rotations*
  would replay in our 3D stage under our own camera, blocking, and props — the
  thing no competitor doing DWPose-to-video can offer.
- It re-implements a retarget that ARDY already owns, in every client, worse.

**Why it belongs on the server.** ARDY already owns cskel27 and already returns
motion in a JSON shape the studio consumes. Extraction on the server means every
client gets it, the retarget stays in one place, and the output is 3D.

**Requested shape** — mirror `/motion/generate` exactly, so the client change is
the source of the motion and nothing else:

```
POST /api/v1/motion/extract
{
  "video_url": "https://…public.mp4",   // R2 URL from /api/v1/media
  "model": "core",                       // same registry as /motion/generate
  "fps": 20,                             // optional; default = the model's fps
  "start_s": 0, "duration_s": 10         // optional trim
}
→ 200  (identical to /motion/generate's response)
{
  "model": "...", "skeleton": "cskel27", "fps": 20,
  "num_frames": 200, "num_joints": 27, "prompt": "", "seed": null,
  "frames": [...]                        // same encoding as generate
}
```

If the response matches `generate`, the studio wires it in ~30 lines: upload →
extract → assign to an actor. Everything downstream — the 3D stage, camera
keyframes, the LTX control take recorder — already works on that type.

**Why it matters beyond convenience.** Authored ARDY motion is the quality
ceiling users are hitting today. Extracted motion from real footage is a step
change, and it keeps the thing competitors can't do: the motion comes from real
video but the *camera and framing stay ours*, because the skeleton is replayed in
our 3D stage rather than baked into someone else's footage.

## 2. Load the `g1` motion checkpoint

`/api/v1/motion/models` reports:

```json
{"nickname":"core","name":"ARDY-Core-RP-20FPS-Horizon40","loaded":true,"fps":20,"skeleton":"cskel27","gen_horizon_frames":40}
{"nickname":"g1","name":"ARDY-G1-RP-25FPS-Horizon52","loaded":false}
```

`core` is 20fps with a 40-frame horizon and is the only thing loaded, so every
take in the product is generated by the smaller checkpoint. Users are reporting
the motion quality directly. `g1` (25fps, horizon 52) is already in the registry
— **is there a reason it isn't loaded, or is it just cold?** If it can be loaded,
that is a free quality improvement across every motion in the studio.

## 3. Document the `ltx-enhance` limits

Two things the model card doesn't say, both of which we are currently guessing at:

**a. Max `width`/`height` — answered, please document.** Job `j-3e7206a490a5`
ran at **1536×896 for the same 1000 cr** as 768×448. Resolution is not priced,
and the studio had been hardcoding the smallest option, which was the entire
cause of the "blurry output" reports. Please state the ceiling on the model card
so nobody re-derives this by spending credits.

**b. `reference_sheet` does not hold identity — what format does it want?**
This is the important one. Same source image (a single full-body character
render on white), two endpoints, opposite results:

| Endpoint | Identity outcome |
|---|---|
| `ltx-2.3 multi_reference` (`images`) | **Held perfectly** — vest, its logo, beanie, beard, all consistent across 240 frames |
| `ltx-enhance` (`reference_sheet`) | **Lost.** The sheet ghosts into roughly the first 25 frames as a semi-transparent double exposure, dissolves, and the subject then renders as a generic shirtless man — the prompt's wardrobe went with it |

So `reference_sheet` behaves like first-frame image conditioning that decays,
not like identity conditioning. Does it expect a specific layout — a multi-view
turnaround grid rather than a single pose? A transparent background rather than
white? A different aspect? As it stands, the pose-controlled flow cannot keep a
character on model, which is the whole premise of the IC-LoRA.

**c. Does `control_video` have to be an ARDY skeleton render?** Still open. If
the Union-Control IC-LoRA conditions on *any* video, say so — that makes real
footage a legal control input directly.

## 4. `wan-s2v lipsync` returns 500 on every call

Two attempts, two different portraits, identical failure. Credits were refunded
both times, so nothing was lost but the flow is unusable.

```
j-25100b2af2bf  full-body render + wav → 500
j-3c5ea8811b24  head-and-shoulders crop + same wav → 500
response={"detail":"Generation command failed (return code 1)"}
for url 'http://localhost:7860/api/lipsync'
```

Both inputs fetched cleanly (the log shows the image and audio downloads
succeeding), and the request the service received looks well-formed:
`num_steps: 35, fps: 24, seed: 12345, face_enhance: True, size: 480*832`. The
failure is inside the generation command. The audio was our own
`voxcpm2-tts` wav, so the two services disagree on something — sample rate or
container is the obvious suspect.

`wan-s2v` is listed in `/jobs/models`, so the studio offers the flow as
available. Any user picking it today gets a 500.

## 5. GPU capacity

Two of three sample renders queued behind GPU pressure, and the TTS job
`j-a914bd68264f` failed outright:

```
waiting_for_gpu — GPU1 has 11.2GB free, need ~14GB — waiting for capacity
FAILED: GPU0 is thermally throttled (temp too high); aborting before compose-up
```

Credits were correctly refunded on the failure, and the surfaced reason was
genuinely useful. Flagging it as a capacity/cooling signal rather than a bug.

## What we did on our side meanwhile

- Chat gained runnable **flow cards**: drop a file on a slot, it uploads to the
  media store and fills itself; the card runs the job and shows the server's own
  `status`/`stage`/`log_tail` as it goes.
- **Video → skeleton** runs locally on MediaPipe (see ask #1) and drops its
  control take straight into the media store.
- `waitForJob` now forwards every poll to its caller — previously it discarded
  `status`, `stage`, and `log_tail`, so no view could show progress.
- Output size, seed, frame count, and `guide_strength` are user-controlled rather
  than hardcoded.
